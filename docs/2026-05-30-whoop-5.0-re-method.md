# WHOOP 5.0 (Gen-5) reverse-engineering method

_A repeatable, on-device method for decoding the WHOOP 5.0 BLE protocol, mirroring how the 4.0 was
decoded in [`../FINDINGS.md`](../FINDINGS.md). Toolkit: [`../re/gen5/`](../re/gen5/)._

> Independent reverse-engineering for interoperability with **your own** device and **your own**
> data (17 U.S.C. §1201(f)); **not** affiliated with WHOOP, Inc. Not a medical device. No
> proprietary WHOOP material is used or reproduced. See [`../DISCLAIMER.md`](../DISCLAIMER.md).

## Why this is a from-scratch effort

The app and decoders in this repo are **WHOOP 4.0 only**. The 4.0's GATT UUIDs
(`61080001-…`), its `[0xAA][len u16 LE][crc8][type][seq][cmd][payload][crc32]` framing, and its
command set are all 4.0 facts established by observing the author's own 4.0. The 5.0 uses a
**different, undocumented** protocol. The only public signal is secondhand
([`FINDINGS.md`](../FINDINGS.md) §6–7): tazjin (Gadgetbridge #5731) reports the 5.0 has ~70
commands and an IMU of "6 integers (X/Y/Z per sensor)", but the **code is unpublished and there
are no UUIDs, no framing, and no scale factors**. So we rediscover it from our own band.

A practical environment note: a cloud/CI box has no Bluetooth — **every step below runs on your own
Mac with the band on your wrist.** Only the offline `analyze_frames.py` runs anywhere.

## Known vs unknown (seed; update as you learn)

| Aspect | Status going in |
|---|---|
| Standard HR `0x2A37` (HR + R-R) | **Likely works unbonded** — SIG-standard, generation-independent. The early win for HRV/recovery. |
| Standard Battery `0x2A19` / Device Info `0x180A` | Likely present (standard profiles). |
| Custom GATT service/char UUIDs | **Unknown** — same `61080001-…` as 4.0, or new? `gen5_gatt_dump.py` decides. |
| Bonding handshake | **Unknown** — 4.0 bonds via one confirmed write to the command char; the 5.0 may differ. |
| Frame format (SOF/length/CRC) | **Unknown** — `analyze_frames.py` tests the 4.0 `0xAA`+LE-length scheme. |
| Command set (~70) | **Unknown** — may partially overlap 4.0 codes; do not assume. |
| Realtime / historical / raw streams | **Unknown** — discover packet types empirically. |
| IMU layout | tazjin: "6 integers" — possibly the same signed int16 X/Y/Z×2 as 4.0; **no scale factors**. |
| Optical / SpO₂ / skin-temp | **Unknown**; on the 4.0 SpO₂/temp are cloud-computed, not on the wire. |

## Step-by-step

All scripts and flags are documented in [`../re/gen5/README.md`](../re/gen5/README.md).

1. **Scan → identify the band.** `python re/gen5/gen5_scan.py` (loudest first). Put the WHOOP
   address into `re/device_local.py` as `GEN5_ADDR`.
2. **GATT dump → map the surface.** `python re/gen5/gen5_gatt_dump.py`. The decisive question: are
   the custom UUIDs `61080001-…` (like the 4.0) or new? Record the command (write) char and the
   notify chars into `re/device_local.py` (`GEN5_CMD_TX_UUID`, `GEN5_CMD_RX_UUID`,
   `GEN5_EVENTS_UUID`, `GEN5_DATA_UUID`).
3. **Standard HR → bank an early win.** `python re/gen5/gen5_standard_ble.py`. If you see live
   `HR=… RR=[…]`, you can already collect HR + R-R for HRV / resting-HR / your own recovery score,
   sub-free, with **no** decoded custom protocol. (This is exactly the 4.0 story in
   `FINDINGS.md` §5.)
4. **Bond + listen.** `python re/gen5/gen5_probe.py --bond-write`. The single confirmed write
   mimics the 4.0 "just-works" bond that unlocks the custom channels. Everything received is logged
   raw to `gen5_probe.jsonl`. Watch which characteristics light up.
5. **Infer the framing.** `python re/gen5/analyze_frames.py re/gen5/gen5_probe.jsonl`. Look for a
   dominant first byte (SOF) + a matching little-endian length header (⇒ 4.0-like — start from
   `protocol/whoop_protocol.json`), or high entropy (⇒ possibly encrypted).
6. **Map the command surface (carefully).** Only after you understand the frame format, use
   `gen5_capture.py`'s control file to send candidate **GET/info** writes one at a time and watch
   the response channel. **Never** send guessed destructive commands (reboot/trim/firmware/ship-mode).
7. **Decode the IMU with a labeled motion capture** — the method that beat prior art on the 4.0
   (`FINDINGS.md` §6, `re/capture_motion.py`):
   - Run `python re/gen5/gen5_capture.py`; enable the raw stream via its control file once you know
     the command.
   - Label phases by writing to `re/gen5/gen5_phase.txt`: 4 static orientations (isolate the
     accelerometer via gravity) + one single-axis rotation per gyro axis.
   - Per int16 position, accel = positions whose mean tracks static orientation; gyro = positions
     quiet when still but spiking in exactly one rotation. Pin scale with a flat-on-table capture
     (‖a‖ = 1 g) and a counted 360°/720° rotation (deg/s).
8. **Record results.** Fill [`../protocol/whoop_protocol_gen5.json`](../protocol/whoop_protocol_gen5.json)
   (it mirrors the 4.0 schema shape) and update `FINDINGS.md`. Wiring the decoders + iOS app to a
   second generation is a later step (see that file's `_wiring` note and
   `ios/OpenWhoop/BLE/BLEManager.swift`, where the 4.0 UUIDs are currently hardcoded).

## What "done" looks like, in stages

- **Stage A (likely quick):** standard HR + R-R flowing → HRV/recovery work on 5.0 data.
- **Stage B:** custom channel bonded, frame format known, command surface mapped, realtime + history
  decoded.
- **Stage C:** IMU offsets + scales pinned; optical/extras as far as the 4.0 got (or further).

Stage A may be enough for the dashboard + Claude features in this repo, since those consume
**computed metrics**, not raw BLE — they're generation-agnostic.

## Result on a WHOOP MG (firmware 50.38.1.0)

First real run of this toolkit against a gen-5 device (a WHOOP **MG**, model `MG`):

- **Open / accessible (no bonding):** the SIG-standard **Heart Rate `0x2A37`** (HR + R-R),
  **Battery `0x2A19`**, and **Device Information `0x180A`** profiles stream to any central.
  HR + R-R confirmed live. This is enough for live HR, **live HRV (RMSSD)**, resting HR, and a
  personal recovery proxy — see `dashboard/gen5_live.py`.
- **Custom service `fd4b0001-cce1-4033-93ce-002d5875f58a`:** present, with the **same 5-channel
  layout as the 4.0** (`fd4b0002` write; `fd4b0003/4/5/7` notify ↔ 4.0 cmd/resp/events/data/memfault).
  But every `fd4b` notify subscription fails with **CBATTError 15 "Encryption is insufficient"** /
  **5 "Authentication is insufficient,"** and the 4.0's just-works confirmed-write bond is
  **refused** (`Insufficient Authentication`). The MG pairs/provisions this channel through the
  **official app (account-tied)** — i.e. it is protected by an **access control.**

**Principled stop.** This project does **not** circumvent access controls (`DISCLAIMER.md`). The
4.0's custom channel was open just-works (reading it was interoperability, not circumvention); the
MG's is encrypted + authenticated, so we **do not** attempt to defeat its pairing/encryption. The
**open standard Heart-Rate profile is the supported live path on the MG.** Raw IMU/PPG/historical
on the MG would require the app's provisioning and are therefore out of scope here.
